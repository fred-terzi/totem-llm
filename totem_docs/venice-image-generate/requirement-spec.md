# Venice Image Generation Skill — Requirement Spec

**Status:** Draft
**Scope:** A new agent skill (`venice-image-generate`) that generates images from a text prompt via the Venice AI `POST /api/v1/image/generate` endpoint and saves the resulting image file(s) into the **per-user agent filesystem sandbox** (`$STORAGE_DIR/totemllm-fs/users/<userId>/images/` in multi-user mode, `$STORAGE_DIR/totemllm-fs/images/` in single-user mode) so the user can see them in their file-system previews / File Explorer. Also emits the existing `fileDownloadCard` websocket event so the image is downloadable directly from the chat. The tool contract **requires the agent to refine the user's idea into a detailed image prompt and present it — together with the credit-cost quote — for user confirmation before the tool is invoked** (F11, F12). Generation is standardized on a single Venice endpoint and model (`POST /api/v1/image/generate`, `z-image-turbo`) so the cost is constant (F13), and in multi-user mode generation is a billed feature: flat quoted credit cost, pre-flight balance check, debit on success only (F14). The refine-and-confirm contract has two enforcement layers: the LLM-level presentation of prompt + quote (F11, instruction-level) and the existing per-invocation tool-approval gate (F10) as the hard checkpoint — the approval card's payload carries the final refined prompt and the exact credit quote, so the user reviews what they are buying before any API call or debit. A `pricing.js` module isolates the cost table so future operations (image editing, video) whose cost depends on size/duration can be added without restructuring. Covers the server-side agent plugin, its registration, skill whitelisting surface, and tests. Does **not** cover image editing / upscaling / background removal (separate Venice endpoints — see Out of scope).
**Depends on:** Per-user filesystem sandbox (`totem_docs/per-user-filesystem/`, ✅ Implemented — `getFilesystemFor(userId)` in `server/utils/agents/aibitat/plugins/filesystem/lib.js`), `VENICE_API_KEY` (already required by the Venice LLM provider, `server/utils/AiProviders/venice/index.js`), create-files `fileDownloadCard` + `registerOutput` pattern (`server/utils/agents/aibitat/plugins/create-files/`), `agentFileServer` download endpoint (`server/endpoints/agentFileServer.js`), File Explorer (`totem_docs/file-explorer/`), Credits ledger (`server/models/credits.js` — `hasCredits`, `debit`, `credit_transactions` table; ✅ Implemented)

---

## 1. Problem

The Totem agent has no way to produce images. When a user asks the agent to "generate a picture of X", the agent can only describe the image in text. Meanwhile:

- The deployment already carries a `VENICE_API_KEY` (used by the Venice LLM provider, `server/utils/AiProviders/venice/index.js:55`), and Venice exposes a text-to-image API (`POST /api/v1/image/generate`) with models (`z-image-turbo`, `nano-banana-*`, `krea-v2-*`, …), style presets, negative prompts, seeds, and multi-variant support — none of it reachable from the agent.
- The per-user filesystem sandbox (`$STORAGE_DIR/totemllm-fs/users/<userId>/`, resolved via `getFilesystemFor(userId)` in `server/utils/agents/aibitat/plugins/filesystem/lib.js:848`) exists precisely so users can see and manage files the agent produces — but the only plugins that write binary output (create-files) write to the **shared** `storage/generated-files/` directory (`server/utils/agents/aibitat/plugins/create-files/lib.js:23`), not into the user's sandbox, and they write documents, not images.
- The File Explorer and filesystem preview tools (`filesystem-read-text-file`, `filesystem-list-directory`, etc.) are scoped to the same sandbox, so an image saved outside it is invisible to the user's normal browsing flow.

## 2. Goal

An enabled agent skill lets the user say "generate an image of a lighthouse at dusk, 16:9" and get a two-step conversation before anything is spent: the agent first refines the idea into a detailed image prompt and presents it with the fixed credit cost, and only generates after the user confirms. On confirmation the user receives the generated image file(s) in two places at once: (1) a download card in the chat (existing `fileDownloadCard` mechanism), and (2) an `images/` folder inside the user's per-user sandbox, visible in File Explorer and to all filesystem tools. Generation parameters (dimensions or aspect-ratio/resolution, negative prompt, style preset, seed, variants, format) are exposed as tool parameters; the model is fixed (F13). In multi-user mode the user's Totem credit balance is charged a flat, quoted cost per successful generation (F14); failures (no API key, insufficient Totem credits, insufficient Venice balance, rate limit, content policy) surface as human-readable tool results and never charge the user.

## 3. Requirements

### Functional

| # | Requirement |
|---|-------------|
| F1 | A new agent skill `venice-image-generate` exposes a `generate-image` tool. The tool accepts: `prompt` (string, required — the final refined prompt presented to the user per F11), `negative_prompt` (string, optional), `width`/`height` (integers, optional, default 1024 each, ≤ 1280), `aspect_ratio` (string, optional — for aspect-driven models e.g. `"16:9"`), `resolution` (string, optional — `"1K"`/`"2K"`/`"4K"`), `cfg_scale` (number, optional, 0 < x ≤ 20), `steps` (int, optional), `seed` (int, optional), `variants` (int 1–4, default 1), `style_preset` (string, optional), `format` (enum `png`/`jpeg`/`webp`, default `png`), `safe_mode` (bool, default true). Only supplied optional parameters are sent in the request body (models pick one sizing idiom — width/height **or** aspect_ratio+resolution — the tool sends whichever the caller supplied, never both). The tool takes **no** `model` parameter — every request uses the standardized model constant (F13). |
| F2 | On success the tool decodes each base64 image in the response's `images[]` array into a Buffer and saves **one file per image** into the invoking user's sandbox at `images/<timestamp>-<sanitized-prompt-slug>[-<n>].<format>` (e.g. `images/20261020-090512-lighthouse-at-dusk.png`), where the sandbox root is resolved per-invocation via `getFilesystemFor(this.super.handlerProps?.userId)` — `users/<userId>/images/` in multi-user mode, shared `images/` under the sandbox root in single-user mode. The directory is created lazily with `recursive: true` on first save. |
| F3 | Every saved image is additionally surfaced in chat via the existing download-card mechanism: `this.super.socket.send("fileDownloadCard", { filename, storageFilename, fileSize })` followed by `createFilesLib.registerOutput(this.super, "ImageDownload", { … })`, matching the create-files pattern (`plugins/create-files/text/create-text-file.js:129-139`). Because the sandbox path is not under `storage/generated-files/`, the plugin writes the bytes itself (through the sandbox `FilesystemManager`) rather than via `createFilesLib.saveGeneratedFile`; the download-card payload therefore carries the sandbox-relative filename. **Investigation note (Step 0 of the plan must resolve):** `agentFileServer.js` currently serves only `{fileType}-{uuid}.{ext}` filenames from `storage/generated-files/`; either (a) a parallel read endpoint for sandbox files is added, or (b) the card links through the existing file-explorer download path. The card must never render as a dead link. |
| F4 | Each file save is announced to the agent with `this.super.introspect(...)` and the tool's final return value reports every file created (name, dimensions in pixels when known, seed when fixed) so the LLM can describe the outcome to the user. |
| F5 | If `VENICE_API_KEY` is unset, the tool returns the standard "disabled because the user has not set it up yet" message (web-browsing pattern) and introspects the reason; no request is made. |
| F6 | API error mapping: `402` → "Insufficient Venice balance", `429` → "Rate limited, retry shortly", `400` → the API's error string verbatim (content-policy violations arrive as 400 with a message), `401` → auth error, `500`/`503` → capacity error suggesting a retry. Network errors and malformed responses produce a tool result the LLM can relay, never a thrown unhandled rejection. |
| F7 | A second tool `list-image-styles` calls `GET /api/v1/image/styles` and returns the style preset names as a JSON list, so the agent can discover valid `style_preset` values at runtime instead of hardcoding them. |
| F8 | The skill is registered in `server/utils/agents/aibitat/plugins/index.js` (named export + slug alias, like every other plugin) and therefore appears in the admin `agent_skill_whitelist` UI. It is opt-in per user/workspace via the existing whitelist; it is not added to `default_agent_skills`. |
| F9 | When `variants > 1`, all N images are saved as separate files with a numeric suffix (`-1`, `-2`, …) and each gets its own download card. `variants > 1` is only honored with JSON base64 responses (always the case here — the tool always uses `return_binary: false`). |
| F10 | **Hard confirmation via the tool-approval gate, with a user-selected "Always allow" path to auto-generation.** The `generate-image` handler invokes the existing per-invocation approval workflow (`this.super.requestToolApproval`, the same gate used by the filesystem write tools — `websocket.js:114` implements it) **before** any Venice API call, balance pre-flight, or debit. The gate call carries: `skillName: "venice-image-generate"`, a `description` that includes the quoted credit cost (e.g. `"Generate an image via Venice AI — costs N credits"`), and a `payload` of `{ prompt: <final refined prompt>, credit_quote: <display-credit integer>, variants, width, height, aspect_ratio, resolution, style_preset, seed }` so the approval card shows the user exactly what will be generated and what it costs. Handler order: availability → quote → **approval gate** → pre-flight (`Credits.hasCredits`) → generate → save → debit. Gate rejection or 2-minute timeout (`TOOL_APPROVAL_TIMEOUT_MS`, treated as rejection by the websocket plugin) produces a rejection tool result with no API call and no debit. **"Always allow" is the designed auto-generate opt-in:** the frontend approval card's "Always allow" checkbox (and the admin whitelist) adds the skill to the user's whitelist (`AgentSkillWhitelist.isWhitelisted`), after which the gate auto-approves and the card is no longer shown — the user has explicitly chosen to let the model auto-generate. This is an intended, documented mode, not an escape hatch: two rules survive it. (1) **F11 still applies** — even for "Always allow" users the agent must still refine the prompt, state the credit quote in conversation, and act only on a confirmed request; "always allow" removes the card, never the conversation. (2) **F14 billing still applies** — pre-flight and debit run in every mode. The card path remains the default for users who have not opted in, so the first generation always shows the card. |
| F11 | **Refine-and-confirm before generation.** The `generate-image` tool description (and any skill-level instructions) mandates this conversational contract: before invoking the tool, the agent refines the user's idea into a detailed image prompt (subject, style, composition, lighting, aspect ratio) and presents it to the user **together with the credit cost quote (F12)**, then waits for the user's confirmation. The tool is never invoked in the same turn the idea is first proposed. Enforcement is instruction-level (tool description text); the approval gate (F10) is the hard checkpoint behind it. The `prompt` parameter passed to the tool must be the refined prompt that was presented. **Interaction with "Always allow" (F10):** users who opted into auto-generation via "Always allow" still get the same conversational refine-and-confirm — the agent must still present the refined prompt and quote and act only on a confirmed request. What "Always allow" removes is the redundant approval card, not the conversation. |
| F12 | **Credit quote.** The cost shown to the user comes from the plugin's `pricing.js` module (`quote(params)`), never hardcoded in prompts or instructions. In multi-user mode the agent must present the quote during the confirm step (F11); the tool's success result reports the exact amount debited. In single-user mode the quote is still presented (so the operator knows the Venice-balance impact) but nothing is debited. |
| F13 | **Single endpoint, single model.** v1 standardizes on `POST /api/v1/image/generate` with the model constant `z-image-turbo` defined in `pricing.js` alongside the cost — one place to change if the standard ever moves. The cost is therefore a flat constant per image. The `pricing.js` schema is keyed by operation name with a `costFor(params)` function per operation, so future workstreams (`venice-image-edit`, video) can register size-, resolution-, and duration-dependent cost functions without touching the tools or the confirmation flow. |
| F14 | **Multi-user billing.** In multi-user mode (`handlerProps.userId != null`): (a) pre-flight — `Credits.hasCredits(userId, quote)` runs before any Venice call; on insufficient balance the tool returns a readable "insufficient credits, this image costs N credits" result with **no** API call and **no** debit; (b) debit — on successful save, `Credits.debit(userId, quote, "venice-image-generate:<veniceRequestId>")` records one `credit_transactions` row; (c) failures after pre-flight (Venice 4xx/5xx, decode errors) never debit. **Admin exemption:** users with the `admin` role are billing-exempt (no pre-flight, no debit), matching the existing chat-endpoint credit gate convention (`server/endpoints/chat.js:66-69`, `Credits.hasCredits` auto-passes admins). In single-user mode (`userId == null`) no pre-flight and no debit — the operator's Venice balance is the meter. Microdollar values never reach tool results or the UI (repo gotcha); the quote and debit use the same display-credit integer the credit badge shows (1 display credit = 1 microdollar in this deployment, so `z-image-turbo` at $0.01/image = 10,000 credits). |

### Non-functional

| # | Requirement |
|---|-------------|
| N1 | **Sandbox isolation is preserved.** All writes go through the user's `FilesystemManager` (path validation, no symlink/traversal escapes). The `images/` subfolder stays inside the sandbox root; the skill must never write outside `$STORAGE_DIR/totemllm-fs/<scope>/images/`. |
| N2 | **Missing-identity behavior (fail-closed on scope, functional fallback):** if `handlerProps.userId` is null/undefined (single-user mode, background/scheduled job), the shared default sandbox (`$STORAGE_DIR/totemllm-fs/images/`) is used — this matches the existing `getFilesystemFor(null)` contract and the single-user deployment model, and is fail-open *by design* for single-user installs only. In multi-user mode a null userId is not expected on the agent path; if it nonetheless occurs, images land in the shared sandbox root rather than being dropped — accepted and documented here because agent sessions in multi-user mode always carry a userId (same assumption the filesystem tools already make). No user-specific secret ever reaches the sandbox path. |
| N3 | **API key reuse, no new secret.** The skill reads `VENICE_API_KEY` from the environment only; it never logs the key, never sends it anywhere except `api.venice.ai`, and adds no new env vars. |
| N4 | **Cost awareness, single source of truth.** All cost logic lives in the plugin's `pricing.js`: one constant for the per-image credit cost of the standardized model (F13), and a `quote(params)` function whose only v1 variable is `variants` (cost = per-image cost × variants, cap 4). The quote presented to the user (F12) and the amount debited (F14) both read from `pricing.js` — they cannot diverge. The constant's value is pinned from Venice's `GET /models` `pricing.generation.usd` for the standardized model and expressed in the display-credit unit. |
| N5 | Filenames are sanitized (prompt slug truncated to a safe length, non-ASCII/unsafe characters stripped, timestamp prefix guarantees uniqueness, numeric suffix for variants); collisions are impossible by construction, and the sandbox `validatePath` still gates the final write. |
| N6 | No database schema changes, no migrations. The `images/` folder appears on disk lazily. |
| N7 | Server-side only (CJS, `require`-style module); no frontend changes beyond what the existing `fileDownloadCard` and File Explorer already render. |
| N8 | Generated images are plain image files in the user's own sandbox — no indexing, no embedding, no upload to any third party beyond the Venice generation request itself. `embed_exif_metadata` stays `false` (default) to avoid writing prompt data into files unless a future workstream opts in. |

## 4. Out of scope

- **Image editing / upscaling / background removal / multi-image composition** — separate Venice endpoints; candidate follow-up skill `venice-image-edit`.
- **Style references (`style_references`)** — requires the agent to read local/remote images into base64 first; deferred to the edit workstream where file I/O is richer.
- **`enable_web_search` image models** — niche, extra charge; not exposed.
- **Size- or duration-dependent credit pricing** (image-editing tiers, video length pricing) — the `pricing.js` schema is designed for it (F13), but those operations do not exist yet; see `venice-image-edit` below.
- **Per-user API keys** — one shared server `VENICE_API_KEY` for v1.
- **The OpenAI-compatible `/images/generations` endpoint** — the Venice-native endpoint covers every needed knob.
- **Automatic gallery UI in the frontend** — File Explorer already previews images in the sandbox.

## 5. Threat model

✅ **Prevents:**
- Sandbox escape via crafted filenames — prompt-derived filenames are sanitized and every write passes the sandbox `validatePath` gate (defense-in-depth on top of construction-time sanitization).
- Cross-user image leakage — in multi-user mode images are written under `users/<userId>/images/` resolved from the session's own `handlerProps.userId`, never from any LLM-controlled parameter (the LLM cannot pass a userId; there is no such tool parameter).
- Secret leakage — `VENICE_API_KEY` is read from `process.env` inside the request headers only; it is never included in introspection messages, tool results, or logs (web-browsing's `middleTruncate` pattern for any accidental key exposure in error params).
- Silent failures — every failure path (no key, API error, decode failure) returns an explicit message to the LLM; no silent no-op.

❌ **Does not prevent:**
- **Spend abuse** — in multi-user mode, bounded by the user's own Totem credit balance (pre-flight check + post-success debit, F14): a user can only spend what they hold. In single-user mode the operator's Venice balance remains the meter. Skill whitelisting (opt-in) still gates access in both modes.
- **Prompt-injection-driven image generation** — if an agent is tricked into calling the tool, the approval gate (F10) blocks it for users who have not opted into auto-generation: the card shows the injected prompt + cost and the user must click Approve; rejection or timeout means no API call and no debit. Residual risks: (a) for users who clicked "Always allow" the gate auto-approves by design — the user explicitly traded the card for convenience, and enforcement falls back to the instruction-level refine-and-confirm flow (F11), which an injected or non-compliant LLM can skip; spend remains bounded by the user's own credit balance (F14); (b) the gate's `payload` (prompt, quote) is LLM-constructed — a malicious agent could show a benign prompt in the payload while sending a different `prompt` to the handler. Accepted: both are bounded by the user's own credit balance (F14), and the card is best-effort UX, not a cryptographic consent surface. Opting back out of auto-generation is possible by removing the skill from the user's whitelist (admin panel), which restores the card on every generation.
- **Pre-flight/debit race** — a concurrent spend between the balance check and the debit could overdraw a user's balance slightly. Accepted (same exposure as chat-turn billing); `Credits.debit` caps at the available balance so balances never go negative.
- **Content policy** — Venice enforces its own content policy server-side (surfaced as 400); Totem adds no filter of its own.
- **Disk growth** — images accumulate in the sandbox with no TTL or quota. Owned by: the per-user filesystem workstream's general storage-hygiene story (same exposure as any user-created file).

## 6. Acceptance Criteria

| # | Acceptance criterion | Maps to |
|---|---------------------|---------|
| AC1 | **Given** `VENICE_API_KEY` is set and the skill is whitelisted, **when** the agent is asked to generate an image, **then** exactly one request is sent to `POST /api/v1/image/generate` with only the caller-supplied parameters merged over `{ model, prompt, format, return_binary: false }`, and one file appears at `images/<timestamp>-<slug>.png` inside the invoking user's sandbox. | F1, F2 |
| AC2 | **Given** a successful generation, **when** the tool completes, **then** the chat shows a download card for the image (no dead link) and the tool result names the file, dimensions/seed when known. | F3, F4 |
| AC3 | **Given** multi-user mode with user 12, **when** user 12 generates an image, **then** the file lands under `$STORAGE_DIR/totemllm-fs/users/12/images/` and is visible via filesystem-list-directory and File Explorer for user 12, while a request from user 13's session cannot reach it. | F2, N1 |
| AC4 | **Given** `VENICE_API_KEY` is unset, **when** the tool is invoked, **then** no HTTP request is made and the tool returns the standard disabled message. | F5 |
| AC5 | **Given** the Venice API returns 402 / 429 / 400 / 401 / 503, **when** the tool is invoked, **then** the tool result contains the mapped human-readable message and the agent session does not crash. | F6 |
| AC6 | **Given** `variants: 3`, **when** generation succeeds, **then** three files (`-1`, `-2`, `-3` suffixes) are saved and three download cards are emitted. | F9 |
| AC7 | **Given** the `list-image-styles` tool, **when** invoked, **then** the style preset names from `GET /image/styles` are returned as JSON. | F7 |
| AC8 | **Given** the tool-approval gate is active (user has not opted into auto-generation via "Always allow", skill not whitelisted and not in `AGENT_AUTO_APPROVED_SKILLS`), **when** the tool is invoked, **then** an approval request is surfaced before any Venice API call, balance pre-flight, or file write; the card's payload includes the final refined prompt and the credit quote, its description names the cost, and it offers Approve/Reject plus the "Always allow" checkbox. | F10 |
| AC9 | **Given** a prompt containing path-hostile characters (`../../etc/passwd`, emoji, newlines), **when** the image is saved, **then** the filename is a safe sanitized slug and `validatePath` confirms the write target is inside the sandbox. | N1, N5 |
| AC10 | **Given** multi-user mode and a first-time image request, **when** the user asks for an image, **then** the agent presents a refined image prompt and the credit cost quote in that turn and does **not** invoke the tool; the tool runs only after the user confirms. Verified in manual E2E plus a unit test asserting the refine-and-confirm instruction is present in the tool description. | F11, F12 |
| AC11 | **Given** a multi-user user whose balance is below the quote, **when** `generate-image` is invoked, **then** no Venice request is made, no `credit_transactions` row is written, and the tool returns an insufficient-credits message naming the cost. | F14 |
| AC12 | **Given** successful generation in multi-user mode, **when** the tool completes, **then** exactly one debit of `quote(params)` (per-image cost × variants) is recorded with reference `venice-image-generate:<requestId>` and the tool result reports the debited amount. Quote and debit read the same `pricing.js` value. | F12, F13, F14, N4 |
| AC13 | **Given** a Venice API failure (e.g. 503) after a passing pre-flight check, **when** the tool completes, **then** no debit is recorded. | F14 |
| AC14 | **Given** single-user mode (`userId == null`), **when** generation succeeds, **then** no `credit_transactions` row is written and no pre-flight check runs. | F14, N2 |
| AC15 | **Given** the user rejects the approval card (or lets it time out after 2 minutes), **when** the tool completes, **then** no Venice request is made, no debit is recorded, and the tool returns the gate's rejection message for the agent to relay. | F10, F14 |
| AC16 | **Given** a user who previously clicked "Always allow" (skill now in their whitelist), **when** they request a confirmed image, **then** the tool auto-approves (no approval card), generation proceeds, billing (pre-flight + debit) still runs, and the tool result reports the debited amount. | F10, F14 |
| AC17 | **Given** the same "Always allow" user, **when** they ask for a new image, **then** the agent still presents the refined prompt + credit quote in conversation and waits for confirmation before invoking the tool (the conversational contract of F11 survives the auto-generate opt-in). | F10, F11 |
